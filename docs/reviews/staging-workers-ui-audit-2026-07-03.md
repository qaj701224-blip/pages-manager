# staging.workers.xd.team UI / 交互走查

日期：2026-07-03

走查方式：使用 Codex 内置浏览器访问 `https://staging.workers.xd.team`，在已登录管理员态下走查桌面端和 390px 窄屏。只做只读交互与非破坏性弹层查看，没有提交创建、保存、撤销、删除、合并等会改数据的动作。

> 说明：本文是 staging UI 走查记录，不是当前产品行为真相源。功能、权限、数据模型和部署边界以 `docs/architecture/xd-cell-console.md`、`apps/pages-api`、`apps/pages-console` 和对应测试为准。截图或走查结论可能随 PR 迭代过期，落地前需要用当前 staging 再确认一次。

## 走查范围

- 首页站点目录：`/`
- 工作台：个人站点、团队站点、团队、Access Keys、账号设置
- 站点详情：概览、部署记录、访问控制、运行配置、设置
- 团队详情：成员、团队 Access Keys、团队设置、添加成员弹层
- 全局操作：主题、语言、通知、用户菜单
- 管理员后台：Dashboard、Ops、用户、站点管理、团队管理、Webhook、审计日志

## 总体结论

当前界面已经有清晰的基础框架：顶部环境提示、工作台/管理员后台侧栏、站点/团队详情页和关键设置表单都可到达。但它更像“工程控制台的最小可用 UI”，在小窗口适配、列表检索、状态语义、危险操作提示、表单反馈和管理后台可扫描性上还不够成熟。

优先级最高的问题是响应式布局。390px 窄屏下顶部导航、账号区、侧边栏和部分表格都会横向溢出；Access Keys 页面文档宽度被撑到约 934px，站点详情和团队详情的侧栏也挤出视口。对内部工具来说，移动端不一定是主场景，但这种溢出也会影响小窗口、分屏和浏览器侧边栏使用。

## 优先级建议

### P1：影响可用性或高风险操作

1. 修复窄屏和小窗口布局溢出。小于 768px 时应把顶部导航、环境提示、账号菜单和侧边栏收敛为移动导航、抽屉或分段导航；表格改为卡片化行、受控横向滚动容器或列裁剪策略，确保页面自身不出现非预期横向滚动。
2. 给破坏性/高权限操作补足上下文和确认流。撤销 Token、删除 Secret、移除成员、删除团队、部门合并、撤销平台管理员等入口需要展示对象、影响范围和恢复性；当前用户、唯一管理员或最后有效访问路径应有额外保护。
3. 管理员后台缺少搜索、筛选、排序和详情入口。用户、站点、团队、审计日志都是跨对象列表，如果数据量上来，没有查找能力会明显降低扫描效率。长 ID 和 metadata 直接铺在表格里，也容易增加误读和误操作。
4. 访问控制仍以 `ACL JSON` 作为高级编辑方式。普通管理员需要理解 JSON 结构和 visibility 枚举含义，缺少结构化 ACL 编辑、示例、校验和保存前预览。

### P2：影响效率、理解和信任感

1. 站点列表缺少搜索、筛选、排序、计数或分组。站点数量稍多时很难快速定位“我负责的、disabled 的、org/internal 的、最近发布的”站点。
2. 状态 chip 语义不够清楚。`owner`、`org`、`internal`、`disabled`、`active` 混在一起展示，容易出现“disabled + active”这类用户难以理解的组合。需要把访问策略和运行状态分开说明。
3. 首页 Sites 与工作台个人站点是两套相近入口，但页面标题、排序和导航归属没有解释差异。
4. 部署记录缺少可行动信息。当前只有部署 ID、来源、状态、时间，缺少失败原因、构建日志、版本详情、发布人和耗时。回滚能力当前未开发，不应在本轮验收中作为必需项；如果后续支持，再补回滚/重试入口。
5. 运行配置的“保存”交互不清晰。环境变量和 Secrets 各有输入区与保存按钮，但没有“添加一条”的明确动作，也没有说明保存后是否立即影响 runtime。

### P3：一致性与细节

1. 通知按钮点击后没有可见面板或空态；主题和语言按钮虽然有菜单，但顶部按钮本身不展示当前状态。
2. 多处空态只有一句话，例如“暂无站点”“还没有 Token”“还没有 Webhook”，缺少下一步建议、文档链接或权限原因。
3. 中英文混排较多：`Access Keys`、`API Token`、`Visibility`、`Status`、`Owner`、`Admin` 与中文标签混用，适合技术用户但不够一致。
4. 长站点名、hostname、内部 ID 和 metadata 的截断策略不统一；有些地方横向撑开，有些地方省略后无法复制完整值。

## 分功能问题

### 1. 全局导航与账号区

- 桌面端顶部导航结构清楚，但环境提示很长，和全局操作挤在同一行。小窗口下会优先挤压用户菜单，导致右侧内容溢出。
- 主题、语言、通知是纯图标按钮。主题和语言有 title / aria-label，通知缺少可见空态；点击通知后只看到按钮 focus 状态，没有消息面板或“暂无通知”提示。
- 用户菜单里的“账号设置”“Access Keys”与侧边栏重复，“管理员后台”又是另一个权限空间。建议在菜单里分组：个人、开发凭证、管理员，并对管理员入口使用更明确的图标和说明。
- 390px 下顶部仍保留 logo、Sites、工作台、环境提示、用户菜单，导致横向溢出。建议移动端只保留 logo + 当前空间 + 菜单按钮，环境标识可收敛为短 chip。

### 2. 站点目录 / 个人站点 / 团队站点

- 站点卡片只有名称、URL、打开图标和状态 chip，没有搜索、筛选、排序、最近更新时间、发布来源等定位信息。
- “打开站点”是右上角外链图标，视觉上较弱；用户可能不知道点击标题进入详情、点击图标打开线上站点。建议标题区和外链区职责更明确，并给 hostname 提供复制按钮。
- 首页站点目录和工作台个人站点展示类似内容，但信息架构上一个属于全站目录、一个属于个人空间。建议明确范围：全部可见站点 / 我的站点 / 我管理的站点。
- 团队站点空态只有“暂无站点”，团队筛选默认 disabled 时应说明原因，例如没有团队、没有团队站点或缺少创建权限。
- 卡片状态 chip 需要分组：归属类型、访问策略、运行状态分别展示，避免把 `disabled` 和 `active` 放在同一层级。

### 3. 站点详情

- 站点详情左侧栏和主标题重复长站点名，小窗口下截断严重。建议侧栏显示短 slug + copy/open 操作，主区展示完整 hostname。
- 概览页是纯定义列表，缺少常用动作：打开站点、复制 hostname、查看最近部署、进入访问控制、查看 runtime 配置。
- 部署记录页信息过少。失败或成功记录都没有可点击详情、日志、错误摘要、部署产物、版本 hash、操作者或 duration。
- 访问控制页上半部分是只读策略，下半部分直接编辑；“保存”即使没有变更也处于可点击状态。建议引入 dirty-state、保存前 diff、visibility 说明和 ACL 结构化编辑。
- 运行配置页中环境变量和 Secrets 的输入区像表单，又像添加区；保存按钮 disabled 时仍然使用强主色，容易误判为可点。建议改为“添加环境变量 / 添加 Secret”行内操作，保存按钮只在有变更时出现。
- Secrets 列表只显示“值已隐藏”和删除按钮。建议补充最近更新人、使用范围、删除确认，以及“覆盖 Secret”的清晰流程。
- 站点设置页显示“暂不支持控制台修改站点设置”，但没有告诉用户应去 CLI、API 还是联系管理员处理。

### 4. Access Keys

- Token 列表缺少使用场景、上次使用时间、创建者、范围、撤销风险说明。只看名称和过期时间，很难判断是否可撤销。
- “更多”菜单只有一个“撤销”项，而且是破坏性动作。建议直接命名为“撤销 Token”，点击后进入确认弹层，确认文案包含 token 名称、归属和影响。
- 新建 Token 弹层中权限默认勾选 `read` 和 `publish`，应解释权限含义、最小权限建议、是否只显示一次 token。空名称时主按钮应有 required 标记和 inline 校验。
- Token preview 适合识别，但不应在文档、日志或截图中传播完整 Token。界面里建议继续只展示短 preview，并提供“复制完整 token”只在创建成功一次性出现的专门状态。
- 团队 Access Keys 空态比个人页更友好，有“新建后用于 CLI / CI”的说明；个人 Access Keys 也应补齐相同层级的说明。

### 5. 团队与成员管理

- 团队列表首次进入有明显加载态，最终布局差异较大。建议用骨架屏或稳定容器高度，避免用户以为卡住。
- 创建团队入口在右上角和列表末尾都出现，意图合理，但文案一个是“创建团队”、一个是“创建新团队”，建议统一。
- 团队卡片缺少成员数、站点数、最近更新时间等判断信息。
- 团队成员页的角色下拉没有明确“自动保存”还是“需要保存”。如果是自动保存，应有保存中/已保存/toast；如果不是，应有统一保存按钮。
- 添加成员弹层默认展示若干用户，搜索输入体验不错，但缺少“无结果”“加载失败”“已筛选”状态。添加按钮是行内低风险动作，但仍需要成功反馈。
- 移除成员和删除团队属于高风险动作，入口应更明确地展示影响范围，并阻止或特别提示移除当前唯一管理员。
- 团队设置页保存按钮在无变更时仍可点，删除团队按钮缺少可见确认前置信息，例如必须输入团队名确认。

### 6. 管理员后台

- Dashboard 指标有价值，但指标卡不可点击，无法从“失败部署 2”直接跳到失败部署列表。
- Ops 页的 `unknown` 状态没有解释含义、影响范围和下一步建议。运维页应该把 unknown / degraded / failed 变成可行动诊断。
- 用户管理页对管理员变更缺少足够确认；当前登录用户和最后平台管理员应有额外保护。用户列表也需要搜索、筛选、排序。
- 站点管理页展示 owner、站点 ID、长 hostname 等信息，扫描密度高但信息层级弱。建议主列展示人类可读信息，内部 ID 收进详情或复制菜单；邮箱或部门名可展示，但不应进入公开导出或截图示例。
- 团队管理页的“部门合并”是高风险批量操作，但表单常驻在列表上方，且“合并”按钮看起来随时可点。建议改为独立流程或至少强制选择源/目标/原因后才可用，并加入确认页。
- Webhook 空态有两个“新建 Webhook”入口，视觉上略重复。空态可以补充 webhook 用途、事件类型、签名安全提示。
- 审计日志直接展示 JSON metadata 和内部 actor ID，适合调试但不适合日常审计。建议提供事件摘要、对象类型、对象名、展开 JSON、复制 ID、过滤条件。

### 7. 账号设置与偏好

- 基本信息页是只读 SSO 同步信息，结构清楚。但移动端姓名和说明被挤成多行，表格式定义列表不适合窄屏。
- 偏好页和顶部主题/语言菜单功能重复，但没有说明两者会同步。建议顶部菜单作为快捷入口，设置页作为完整偏好页，并统一当前状态展示。
- 偏好保存似乎是即时生效，但页面没有“已保存”反馈。对主题/语言这类即时设置，可以在切换后显示轻量 toast。

## 横切建议

1. 建立状态语义规范：访问策略、运行状态、角色、环境、危险级别分别使用不同 chip 样式和文案。
2. 为数据量可能超过 10 条的列表页补统一工具条：搜索、筛选、排序、刷新、计数、空态、错误态。少量静态列表可以先提供明确范围说明。
3. 为表单补 dirty-state、required 标记、inline error、保存中、成功和失败反馈；只读表单应明确说明数据来源。
4. 对长 ID / hostname / JSON 使用“摘要 + 展开 + 复制”的模式，而不是直接铺满表格。
5. 小窗口采用统一 shell：顶部短导航、侧栏抽屉或分段导航、表格卡片化、环境标识收敛。
6. 给图标按钮补可见 tooltip 和明确 aria-label；通知按钮需要真实 popover 或空态。

## 建议落地顺序

1. 先修响应式 shell 和横向溢出：这是最显眼、也最容易建立质量感的问题。
2. 再做站点卡片和状态 chip 语义：会立刻提升站点目录、个人站点、团队站点的识别效率。
3. 然后做列表页统一工具条和管理后台表格扫描能力：优先覆盖用户、站点、团队、审计日志。
4. 再处理高风险操作确认：撤销、删除、合并、移除成员、保存访问策略。
5. 最后改造复杂表单：ACL 结构化编辑、环境变量/Secrets 添加流程、审计日志详情化。

## 验收检查点

- 390px、768px、1280px 三个宽度下页面不出现非预期横向滚动。
- 数据量可能超过 10 条的列表有搜索、筛选或清晰范围说明，空态有下一步动作。
- 所有破坏性操作都有二次确认，并在确认文案里包含对象名称和影响范围。
- Access Keys、Secrets、审计日志不会在文档、普通导出或日志中暴露完整敏感值。
- 表单无变更时保存按钮禁用或隐藏；保存后有成功/失败反馈。
- icon-only 按钮有 tooltip、aria-label 和 keyboard focus 状态。
