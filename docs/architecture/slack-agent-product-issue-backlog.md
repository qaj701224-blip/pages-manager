# Slack Agent Repo 级产品问题 Backlog

本文记录 Slack 试用中暴露的产品和闭环问题。当前作为后续逐项修复的输入；每个问题是否已落地以“当前进展”为准。

## 目标体验

Slack Agent 的目标不是一个“个人站点发布助手”，而是 pages-manager repo 的研发入口。用户在 Slack 中只需要表达自然语言需求，系统应清楚回答三件事：

- 当前理解了什么
- 现在卡在哪个阶段
- 用户下一步能做什么

除非用户明确需要排障细节，否则不暴露 gateway、worker、MySQL、callback、内部状态卡等底座概念。

后续 CF / 个人站点 / Pages v2 / Slack / CI / 部署脚本 / 文档都不再用目录做产品边界。Slack 可以为整个 repo 创建 Issue、推动 PR 和自动开发。真正的边界应该是权限、风险等级、审批、测试和部署策略：

- 低风险文案、配置、站点内容修改可以自动进入开发
- CF runtime、个人站点发布链路、GitHub Actions、部署脚本、K8s、权限与 secret 相关改动必须标记为高风险
- 高风险不代表不能改，而是需要明确审批、审计记录和更强测试
- 生产部署仍应独立于 Slack 自动开发，不能因为 Slack 创建需求就自动发布生产

## 产品对象模型

后续应收敛为一个统一的 Work Item，而不是“个人站点任务”和“平台需求”两套用户心智。

用户可见对象：

- Work Item：一次需求、问题、改造或反馈
- Issue：需求的 GitHub 记录
- PR：代码实现
- Check：CI / Review / 测试结果
- Deployment：预览或生产发布结果

内部可以继续保留不同实现 lane，但 Slack 用户不需要理解 lane。用户只需要看到：

- 任务标题和摘要
- 当前阶段
- Issue / PR / Preview / Check 链接
- 是否需要确认
- 下一步动作

## 待处理问题

### 1. 查询个人 Issue / PR 时 gateway 报错

当前进展：已修复基础容错和 issue 列表范围。`list_my_work_items` 会过滤 stale / missing work item，列表渲染前也会跳过空项；全部为空时返回空态，不再让 Slack 只显示失败表情。用户明确问“我的 issue 有哪几个 / 多少个”时默认查询全部可见 issue，而不是只查可继续任务；列表结果会写入会话记忆，后续“只有这一个么 / 还有吗”沿用上一轮列表范围继续查询。

用户问题：

```text
目前我个人有哪些 issue？
当前会话有哪些？
```

ECS 日志结论：

- Slack Agent 已正确识别为 `list_work_items`
- 模型调用结果是 `ok`
- 失败发生在 gateway 执行查询工具之后
- gateway 报错：`Cannot read properties of null (reading 'status')`

产品影响：

- 用户看到 Bot 说“我来帮你查询...”，但没有得到列表
- Slack 最终只显示失败表情，用户不知道失败原因
- 这会被误认为 Slack Agent 理解失败，实际是工具执行链路没有兜底

建议修复方向：

- `list_my_work_items` 必须容忍 stale link、缺失 job、缺失 platform item
- 列表渲染前过滤 `null / undefined`
- 找不到任务时返回空态文案，而不是后台异常
- 明确询问 issue 数量或清单时返回当前用户可见的全部 issue / PR 状态，不要求用户先说“历史”或“全部”
- 对上一轮列表的短追问必须沿用列表上下文，不重新澄清“哪个对象”
- 失败时给用户一个简短可理解的结果，例如“暂时没查到可继续的任务，我已记录这次查询失败”
- gateway 日志补充 eventId、sessionId、tool name、stack，便于排障

### 2. 已经有表情反馈，还出现“正在整理需求...”

当前进展：已修复查询类自然语言 turn 的错误占位。短查询、任务列表、状态、诊断和重试类问题只用 reaction 作为处理中提示，结果出来后直接回复列表、诊断或空态；需求整理类 turn 仍可使用可更新的 Agent 回复。

现象：

- 用户发出查询类问题后，消息上已有“处理中”表情
- Bot 又发一条正文：“正在整理需求...”

产品问题：

- 同时出现 reaction 和正文进度，信息重复
- “当前会话有哪些？”是查询，不是需求整理，“正在整理需求”语义不准确
- 如果后续执行失败，用户只看到一个泛化的处理中消息，无法判断到底在查什么

建议产品规则：

- 短查询类操作只用表情作为处理中提示，完成后直接回复结果
- 真正长任务才创建一条可更新的状态消息
- 查询类文案应按动作区分，例如“正在查询...”而不是“正在整理需求...”
- 同一轮交互只保留一个主要进度载体：reaction 或状态消息二选一

### 3. Issue 创建后，用户不知道是否已经进入 PR / 自动开发

当前进展：已补齐当前任务诊断入口。用户询问“为什么没成功 / PR 为什么没出来 / 查日志 / 能不能重试”时，会返回任务诊断报告，展示 Issue、PR、Preview、Workflow、当前阶段、可能原因、受控日志摘要和下一步动作；重试、追加诊断到 Issue、转人工排查都通过按钮执行，不由自然语言 turn 直接触发。

现象：

- 用户确认需求后，系统创建 Issue
- 用户不清楚是否已经创建 PR，也不清楚自动开发是否开始

产品问题：

- Issue、PR、自动开发、CI、Review 是不同阶段，但 Slack 没有把阶段讲清楚
- “Done” 表情不足以表达“只是 Issue 创建成功”还是“已经完成开发”

建议产品规则：

- Issue 创建成功后明确展示：
  - Issue 链接
  - 当前阶段
  - 下一步是等待用户触发自动开发、正在自动开发，还是等待 PR
- PR 尚未创建时必须明说“PR 尚未创建”
- PR 创建后再更新同一任务卡，展示 PR 链接、CI 状态和 Review 状态
- 对 CF / 个人站点 / 平台代码都使用同一套阶段表达，不要让用户先判断这是哪个 lane

### 4. Slack Agent 看起来像关键词匹配，而不是 Agent

现象：

- 用户觉得 Slack Agent 曲解了意图
- 当前行为更像根据固定关键词选择流程，而不是理解上下文

产品问题：

- 过多依赖 intent / toolCall 固定分支时，用户会感觉不自然
- 自然语言补充、追问、纠偏没有被充分融合到同一个任务上下文里
- Agent visible reply 有时像模板话术，缺少对用户原意的确认

建议产品规则：

- Slack Agent 应先做语义理解和任务归纳，再选择工具
- 确定性规则只作为安全边界和兜底，不应主导所有表达
- 对用户可见文案要复述真实需求，而不是暴露分类结果
- 对模糊请求优先追问一个关键问题，不要过早落到错误工具
- Agent 可以判断影响范围是 CF、个人站点、CI、Slack 还是文档，但这些应作为任务元数据，不应变成用户必须理解的入口分类

### 5. 卡片文案重复，确认后动作不清晰

现象：

- 确认卡、状态卡、thread 回复中存在重复文案
- 用户点击确认后，不知道系统接下来会做什么

产品问题：

- 卡片像多个独立通知，而不是一个连续任务
- “需求确认”后缺少明确阶段转移

建议产品规则：

- 确认前：只展示需求摘要、风险、影响范围、确认按钮
- 确认后：原卡片或同 thread 后续消息明确进入下一阶段
- 避免重复展示同一段摘要
- 任务主卡只保留当前状态、关键链接、下一步动作

### 6. 二次补充后 Issue 没变化，Slack 只显示 done

当前进展：Platform Dev Lane 的已绑定 Issue / PR follow-up 会把补充写入 Issue comment，并触发后续自动修复；诊断报告里的“追加诊断到 Issue”按钮也会写入用户可见诊断摘要。站点发布 lane 与 PR comment 的统一策略还需要继续收敛。

现象：

- 用户补充需求后，Slack 只用表情表示 done
- Issue 没有新增 comment 或状态变化
- 用户不知道补充内容是否进入任务

产品问题：

- done 表情不能代表“补充已写入 Issue”
- 对异步开发任务来说，补充必须有可追踪记录

建议产品规则：

- 对已绑定 Issue / PR 的任务，二次补充必须写入对应 Issue comment 或 PR comment
- Slack 回复中明确说明补充已记录到哪里
- 如果写入失败，必须给出可操作失败提示
- 如果当前会话没有绑定任务，应提示用户先选择一个 Issue / PR

### 7. CF / 个人站点改造不应被排除在自动开发之外

现象：

- 过去设计里有“个人站点发布 lane”和“平台开发 lane”的边界
- 这会让 CF runtime、Pages v2、个人站点发布能力看起来不能通过 Slack 改

产品问题：

- 用户视角是“帮我改 pages-manager 这个产品”，不是“我先判断要走哪个 lane”
- CF / 个人站点发布链路本身也是 repo 的产品能力，应该能被 Slack 创建 Issue、推动 PR、跑测试
- 目录隔离只能约束自动生成的用户站点内容，不应限制 repo 级研发入口

建议产品规则：

- Slack 创建的是 repo 级 Work Item，可以覆盖全 repo
- 系统自动识别影响范围：CF runtime、用户站点发布、Slack 体验、CI/CD、部署、文档等
- 影响范围决定风险等级、审批和测试矩阵，不决定能不能创建任务
- 对 CF / 发布链路的改动必须强制跑对应 regression tests，并在卡片里展示“需要验证发布链路”
- 生产发布仍需人工触发或明确发布审批；自动开发最多创建 PR，不自动上线

### 8. 风险和权限需要替代目录边界

现象：

- 如果全 repo 都可改，原先靠目录隔离表达安全边界已经不够

产品问题：

- 没有清晰风险模型时，系统要么过度保守，什么都不能自动改；要么过度开放，workflow / deploy / secret 相关改动风险过高

建议产品规则：

- 每个 Work Item 都必须有 risk、affected areas、required checks、approval policy
- 高风险范围包括但不限于：CF runtime、公开 API、GitHub Actions、部署脚本、K8s、权限、secret、token、生产发布链路
- 高风险可以进入自动开发，但必须先确认，并在 PR 中明确风险与测试
- Slack 里“自动开发”触发的含义必须精确：点击自动开发不等于批准合并，不等于批准生产发布
- 合并和生产发布应保持独立权限

### 9. 测试闭环需要从 lane 维度改成影响范围维度

现象：

- 当前容易按 site lane / platform lane 思考测试
- 全 repo 研发入口需要按实际影响范围选择测试

产品问题：

- 改 Slack 文案只跑 Slack 测试即可
- 改 CF runtime 必须跑 server / SDK / public docs / deploy safety 相关测试
- 改 CI workflow 必须跑 workflow policy tests
- 改个人站点发布链路必须跑 Issue -> PR -> Preview / site-check 相关测试

建议产品规则：

- Work Item 生成时产出 required checks
- PR 创建后 Slack 展示 required checks 的结果
- CI 失败时 Slack 能解释失败阶段和下一步
- 用户不需要懂测试文件名，但需要知道“哪些能力已经验证”

## 后续拆分建议

优先级建议：

1. 先修复查询任务列表异常，避免基础查询红叉
2. 再统一 reaction / 进度消息策略，减少重复反馈
3. 补齐 Issue -> PR -> 自动开发 -> CI -> Review 的阶段表达
4. 优化二次补充写入 Issue / PR 的可见闭环
5. 把“个人站点 / 平台需求”用户心智收敛成统一 Work Item
6. 用影响范围、风险、审批、测试替代目录边界
7. 最后调整 Slack Agent 的 prompt 和工具选择边界，让自然语言体验更像任务助理

验收口径：

- 用户问“我的 issue / PR / 当前会话有哪些”时，必须得到列表或空态
- 每个任务都能清楚看到 Issue、PR、当前阶段和下一步
- 查询、确认、补充、失败都不能只靠表情表达最终结果
- Slack 对用户的文案不暴露内部底座名称
- 用户可以通过 Slack 对 CF / 个人站点发布链路提出改造需求，并进入 Issue -> PR -> CI -> Review 闭环
- 高风险改动可以被创建和开发，但审批、测试、合并、发布边界必须清楚
