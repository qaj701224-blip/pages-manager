# XD Cell 控制台前端设计规范

本文定义 XD Cell 控制台前端开发、评审和验收的 UI / 交互规范。它适用于 `staging.workers.xd.team` / `workers.xd.team` 控制台、工作台、站点详情、团队管理、Access Keys、管理员后台，以及后续同类内部管理界面。

本文归属 `apps/pages-console` 领域；全局 `docs/README.md` 只保留索引入口。相关走查输入见 [`docs/reviews/staging-workers-ui-audit-2026-07-03.md`](../../../docs/reviews/staging-workers-ui-audit-2026-07-03.md)。

## 设计目标

XD Cell 控制台是内部站点发布和管理工具，不是营销站点。前端设计优先级如下：

1. **清晰**：用户能快速判断当前空间、对象、状态、权限和下一步动作。
2. **稳定**：布局不因长名称、长 ID、空态、加载态或窄屏而错位。
3. **可扫描**：列表、表格、详情页能支持快速查找、比较和定位。
4. **低误操作**：高风险操作必须有上下文、确认和可恢复提示。
5. **可审查**：前端 PR 能用本文 checklist 做明确验收。

## 信息架构

- 控制台必须明确区分三个空间：公开站点目录、个人/团队工作台、管理员后台。
- 顶部导航只放全局入口：品牌、主空间入口、环境提示、全局操作、用户菜单。
- 侧边栏只放当前空间内的二级导航。进入站点详情或团队详情后，侧边栏应切换为该对象的局部导航。
- 页面标题必须反映当前对象或任务，例如“个人站点”“Access Keys”“站点管理”，不要只用笼统的“设置”。
- 首页 Sites 与工作台站点列表必须说明范围差异：全部可见站点、我的站点、我管理的站点或团队站点。

## 布局与响应式

- 所有控制台页面必须通过 `390px`、`768px`、`1280px` 三个宽度验收。
- 页面不得出现非预期横向滚动。只有表格或代码块这类明确容器可以横向滚动，并且容器边界必须可见。
- 小于 `768px` 时，侧边栏必须收敛为抽屉、顶部菜单或分段导航；不能把桌面侧边栏挤出屏幕。
- 小于 `768px` 时，顶部环境提示必须收敛为短 chip，例如 `Staging`，详细说明放入 tooltip 或环境菜单。
- 主内容区应使用稳定宽度和间距。卡片、表格、表单不能依赖内容撑开布局。
- 长 slug、hostname、部署 ID、用户 ID、metadata 必须有截断、复制和展开策略。

## 视觉风格

- 控制台使用克制、工具型视觉。避免大面积装饰背景、营销式 hero、过度渐变和低信息密度卡片。
- 主色只用于主操作、当前导航态和关键状态提示。危险操作使用独立危险色，不与主色混用。
- 卡片用于对象项、弹层、表单区块和空态容器；不要把页面大区块层层套成卡片。
- 图标按钮必须有 tooltip 和 `aria-label`。常见操作优先使用图标：打开、复制、刷新、删除、更多、关闭。
- 文字大小应匹配容器密度。列表、表格、侧栏和弹层内不要使用 hero 级标题。

## 列表与表格

站点、Token、团队、用户、审计日志、部署记录等列表必须满足：

- 数据量可能超过 10 条，或列表覆盖多个用户/团队/站点时，必须提供搜索、筛选、排序或清晰范围说明。
- 有总数或当前筛选结果数量。少量对象列表可以先只展示总数或范围说明。
- 有加载态、空态和错误态。空态必须包含下一步动作、为空原因或权限说明。
- 表格列必须按“人类可读信息优先，内部 ID 次级”的原则排序。
- 内部 ID、JSON、metadata 不直接铺满表格。默认展示摘要，详情通过展开、抽屉、弹层或复制按钮提供。
- 状态列必须使用统一 chip，不要只用裸文本。
- 行级危险操作不能只藏在“更多”里；菜单项必须写清动作，例如“撤销 Token”“删除 Secret”。

## 状态语义

状态 chip 必须按语义分组，不同组不能混用同一种样式：

| 语义 | 示例 | 展示规则 |
| --- | --- | --- |
| 环境 | `staging`、`production` | 顶部环境提示，生产环境必须更醒目 |
| 访问策略 | `owner`、`org`、`internal`、`acl`、`disabled` | 说明访问范围，不等同于运行状态 |
| 运行状态 | `active`、`disabled`、`failed`、`pending` | 说明对象是否可用或执行是否成功 |
| 角色 | `viewer`、`publisher`、`admin` | 说明当前用户或成员权限 |
| 风险级别 | `danger`、`warning`、`info` | 用于确认弹层、警告和不可逆操作 |

如果一个站点同时显示 `disabled` 和 `active`，界面必须解释它们分别属于访问策略和运行状态，或改成更明确的文案。

## 表单与保存

- 表单字段必须有 label；placeholder 不能替代 label。
- 必填字段必须明确标记，并有 inline 校验。
- 保存按钮在无变更时应禁用或隐藏；禁用态不能使用强主色造成可点击误判。
- 保存流程必须包含保存中、成功、失败状态。失败提示必须告诉用户下一步。
- 会影响 runtime、访问控制、权限或密钥的保存操作，必须说明生效范围和生效时机。
- 自动保存控件必须显示保存反馈；非自动保存控件必须有明确保存按钮。
- JSON 编辑只可作为高级模式。默认应提供结构化编辑、示例、校验和格式化。

## 高风险操作

以下操作必须二次确认：

- 撤销 Token 或 Access Key。
- 删除 Secret、环境变量、Webhook。
- 移除成员、提升为 `admin`、撤销平台管理员。
- 删除团队、部门合并、转移团队资产。
- 修改站点访问策略、ACL、运行配置。
- 禁用站点、恢复站点；回滚/重试仅在对应能力上线后纳入确认流程。

确认弹层必须包含：

- 操作对象名称。
- 影响范围。
- 是否可恢复。
- 操作后用户应如何验证结果。

删除、撤销、合并这类不可逆或高影响操作，应要求输入对象名称、选择原因或至少使用明确的危险按钮文案。禁止在当前唯一管理员、当前登录用户或最后一个有效访问路径上提供无保护的危险操作。

## Access Keys 与敏感信息

- Token、Secret、cookie、session、完整 access key 不得在普通列表、日志、文档、截图或导出中显示。
- Token 列表只展示短 preview、名称、范围、创建时间、过期时间、上次使用时间和创建者。
- 新建 Token 成功页必须说明完整 token 只显示一次，并提供复制操作。
- 权限默认值必须遵循最小权限原则。默认包含 `publish` 时，必须解释它用于 CLI / CI / agent 发布，不代表可绕过团队或站点权限。
- 撤销 Token 前必须显示它的归属、权限、最近使用时间和影响范围。
- 用户邮箱、部门路径属于内部身份信息，可以在受控控制台内用于识别 owner；不要写入公开文档示例、普通导出或不必要的日志。

## 空态、加载态和错误态

- 加载态应尽量使用骨架屏或稳定容器高度，避免加载完成后大幅跳动。
- 空态必须回答三个问题：为什么为空、用户能做什么、是否需要权限或团队条件。
- 错误态必须包含错误摘要、可能原因、重试入口和必要时的排障链接。
- 权限不足不能只显示空态；必须明确说明当前角色缺少什么权限。
- 网络或接口失败不能无限显示“加载中”。

## 弹层、菜单和抽屉

- 弹层用于短流程，不承载复杂多步配置。复杂流程应使用独立页面或抽屉。
- 弹层必须有明确标题、关闭按钮、取消按钮和主操作按钮。
- 菜单项必须用动词或名词短语表达真实动作，避免只有“撤销”“更多”这类模糊文案。
- 点击通知按钮必须出现通知面板或“暂无通知”空态，不能只有 focus 状态。
- 抽屉适合详情预览、JSON metadata 展开、审计日志详情、部署详情。

## 文案规范

- 默认使用中文。产品名、API 名、CLI 命令、权限枚举和代码字段可保留英文。
- 按钮使用动词：`新建 Token`、`保存访问策略`、`撤销 Token`、`复制 Hostname`。
- 状态使用用户能理解的文案。必要时保留技术枚举，但要补充解释。
- 错误信息必须给出可执行下一步，例如“重试”“检查权限”“重新登录”“联系平台管理员”。
- 不要在界面或文档中输出真实 secret、完整 token、cookie、session、Cloudflare 资源 ID 或内部凭证。

## 可访问性

- 所有 icon-only button 必须提供 `aria-label` 和 tooltip。
- tab、menu、dialog、combobox 必须支持键盘操作。
- 当前导航项、当前 tab、当前筛选条件必须有明确视觉状态和语义状态。
- focus ring 必须可见，不能只依赖颜色变化。
- 表单错误必须能被屏幕阅读器关联到对应字段。
- 颜色不能作为唯一状态表达方式，必须配合文字或图标。

## 开发实现约束

- 新增页面前先确认是否已有 shell、列表、表单、弹层、状态 chip、空态模式可复用。
- 不为单一页面临时创造一套视觉语言。样式变量、间距、颜色、圆角、阴影必须复用已有约定。
- 长内容必须在实现时考虑：slug、hostname、部署 ID、邮箱、JSON metadata、错误信息。
- 表格实现必须包含小窗口策略：卡片化、列裁剪、详情抽屉或受控横向滚动。
- 任何保存、删除、撤销、合并操作都必须有测试或可手工验证路径。
- 修改公开交互时，同步更新相关文档、CLI/help/skill 边界说明（如适用）。

## PR Self-review Checklist

前端 PR 必须在描述中说明以下检查结果：

- [ ] `390px`、`768px`、`1280px` 下无非预期横向滚动。
- [ ] 列表和表格有搜索、筛选、计数、空态或合理范围说明。
- [ ] 状态 chip 按环境、访问策略、运行状态、角色、风险级别分组展示。
- [ ] 表单有 label、required、inline error、保存中、成功和失败反馈。
- [ ] 高风险操作有二次确认，确认文案包含对象、影响范围和恢复性。
- [ ] icon-only button 有 tooltip、`aria-label` 和可见 focus 状态。
- [ ] 长 ID、hostname、JSON、metadata 有摘要、复制或展开策略。
- [ ] 空态、加载态、错误态不会让用户误以为页面卡死。
- [ ] 不在 UI、日志、文档或截图中暴露完整 token、secret、cookie、session 或真实凭证。
- [ ] 行为变更已有 focused 测试或明确手工验收路径。

## Review 重点

评审前端 PR 时，先看 P0/P1 风险：

- 是否可能泄露 token、secret、session、内部资源 ID 或跨用户 metadata。
- 是否让 production / staging 环境语义混淆。
- 是否让访问控制、ACL、权限或危险操作变成 fail-open 或可误点。
- 是否缺少响应式验证导致小窗口不可用。
- 是否修改了用户可见行为却没有测试或验收路径。

风格偏好排在后面。只有当视觉差异影响信息层级、可读性、可访问性或误操作风险时，才作为阻断问题提出。
